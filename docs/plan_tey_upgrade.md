# `tey upgrade` — self-update for Tey

## Context

Tey (`tey/`) is Kex's own package/toolchain manager. It already manages
**Kex** toolchains fully (`tey kex install/use/uninstall/list`), but it
cannot manage **itself**. `docs/tey-limitations.md` states this outright:

> Tey cannot yet manage Tey. It is installed and upgraded by whatever
> installed it, and there is no `tey self update` — so the toolchain manager
> is the one thing on the machine that is not under the toolchain manager.

This plan closes that gap with a command spelled **`tey upgrade`** (not
`tey self update`). It finds the newest released Tey, downloads and
checksum-verifies the same archive the release workflow publishes, and swaps
it into place for a plain tarball/`make install` install — while explicitly
declining to touch a Homebrew-managed install (that keg is `brew`'s to
upgrade).

Out of scope, deliberately: `--pre` / a pinned version argument. Bare
`tey upgrade` → newest stable, mirroring bare `tey kex install`. Can be added
later the same way `kex install [latest|<version>]` was, but nothing today
asks for it.

## How Tey finds itself and the release, without new infrastructure

Everything below reuses patterns already in `tey/src/tey/toolchain.kex`
rather than inventing new ones:

- **Which Tey is running / where it's installed**: `tey/bin/tey` (the
  installed launcher shim) already exports `TEY_EBIN=$PREFIX/lib/kex/tey/ebin`
  before invoking the BEAM. `Tey.Version.number` (generated by
  `tey/Makefile` from `tey/package.kex`) is the running version. So:
  `PREFIX` = `ENV.get("TEY_EBIN")` with the trailing `/lib/kex/tey/ebin`
  stripped. If `TEY_EBIN` isn't set (dev checkout, `make check`, someone
  invoking `erl` by hand), refuse with a clear error — there's nothing safe
  to overwrite.
- **Refusing a Homebrew install**: if `PREFIX` contains `/Cellar/` (covers
  both macOS Homebrew and Linuxbrew), refuse and point at `brew upgrade tey`
  — matches how `docs/tey-limitations.md` already describes that path as
  brew's responsibility, and avoids Tey fighting the keg's bookkeeping.
- **Finding the newest released Tey version, without hitting the GitHub API**
  (the codebase deliberately avoids `api.github.com` elsewhere — Kex release
  discovery goes through `git ls-remote --tags`, not the REST API, to dodge
  auth/rate limits):
  1. `Tey.Toolchain.latestStable` already resolves the newest released **Kex**
     tag from git tags — no clone, no API.
  2. Tey's own version doesn't move in lockstep with Kex's, but Tey ships
     from the same repository on every release, so the manifest at that same
     tag names Tey's current version. Fetch
     `https://raw.githubusercontent.com/<owner>/<repo>/<tag>/tey/package.kex`
     (a plain CDN GET, same `curl -fsSL` idiom `Tey.Toolchain.download`
     already uses — no git API, no rate limit) and pull the version out of
     its `version("...")` line, the same value `tey/Makefile`'s `sed` line
     and `.github/workflows/release.yml` already extract from that file.
  3. `<owner>/<repo>` is `Tey.Toolchain.repository` with the `https://github.com/`
     prefix and `.git` suffix stripped — same assumption `releaseBase`
     already makes (GitHub-shaped URL).
  4. Compare that version to `Tey.Version.number`. Equal → print "Tey X is
     already the newest version" and exit 0 (mirrors `Tey.Cli.alreadyCurrent`
     for Kex). Different → proceed.
- **Downloading and verifying the archive**: `tey-<version>.tar.gz` and its
  `.sha256` are published beside the Kex archives under the *same tag*
  (`.github/workflows/release.yml:308-317`), at exactly the URL shape
  `Tey.Toolchain.releaseBase` already builds
  (`<releaseBase>/<tag>/tey-<version>.tar.gz[.sha256]`). Reuse
  `Tey.Toolchain.download` and `Tey.Toolchain.verifyArchive` verbatim.
- **Extracting**: same `tar -xzf` into a staging dir under
  `Tey.Cache.root/downloads` that `installArchive` already uses, sanity
  checked for `bin/tey` and `lib/kex/tey/ebin` being present (mirrors the
  existing `bin/kex` presence check).
- **Swapping into PREFIX**: the archive's internal layout
  (`tey-<version>/{bin/tey,bin/kex,lib/kex/tey/ebin/*.beam}`) is exactly a
  relocatable install prefix — the same shape `make install` produces and
  `.github/actions/setup-tey/action.yml` already unpacks by copying wholesale
  into a dedicated `dist/` it owns. Self-update differs because `PREFIX` here
  (e.g. `/usr/local`) is **not exclusively Tey's** — it can hold unrelated
  binaries — so, unlike `Tey.Toolchain.publish` (which safely renames an
  entire toolchain directory it fully owns), this must replace only three
  specific paths, each with an atomic rename-over:
  - `<PREFIX>/lib/kex/tey/ebin` — a directory Tey *does* own exclusively, so
    this one **does** reuse `Tey.Toolchain.publish(stagedEbin, currentEbin)`
    as-is (stage-aside/rename/rollback-on-failure).
  - `<PREFIX>/bin/tey` and `<PREFIX>/bin/kex` — individual files sitting
    beside potentially unrelated binaries, each swapped with a plain
    `FS.File.rename(extractedFile, targetPath)` (POSIX rename atomically
    overwrites an existing target — the same pattern `Tey.Toolchain.download`
    already relies on for `partial → path`). No directory-level rename here.
  - Because every `tey` invocation is a fresh short-lived `erl` process that
    loads its `.beam`s at startup, overwriting these files mid-run does not
    disturb the *currently running* `tey upgrade` process — the new files
    simply take effect on the next invocation. This is the same safety
    property the existing Kex-toolchain swap already depends on.

## Changes

1. **`tey/src/tey/toolchain.kex`** — promote `download`, `verifyArchive`,
   `checksumOf`, and `releaseTag` out of the trailing `private do...end`
   block to plain public `foul`s (unindented, same as `releaseBase`,
   `installedVersions`, etc. already are). No behavior change; this only
   makes them callable from the new module below, which needs the exact same
   download/verify/tag-resolution logic Tey already trusts for Kex archives.

2. **New file `tey/src/tey/selfupdate.kex`**, `module Tey.SelfUpdate`,
   alongside `toolchain.kex` (same one-module-per-concern layout the rest of
   `tey/src/tey/` follows — see the file list in `docs/plan_tey_pm.md`'s
   "Tey's own module structure"). Public surface:
   - `foul currentPrefix -> String?` — `TEY_EBIN` with the
     `/lib/kex/tey/ebin` suffix stripped, or `None` if unset/malformed.
   - `foul homebrewManaged?(prefix: String) -> Bool` — `prefix.contains?("/Cellar/")`.
   - `foul latestVersion -> String or! String` — implements the
     raw.githubusercontent.com manifest-read described above; returns the
     Tey version string.
   - `foul upgrade -> Void or! String` (or an `Integer` exit-code style
     matching `Tey.Toolchain.installRelease`'s callers) — orchestrates:
     resolve prefix → refuse if Homebrew/unset → resolve latest version →
     compare to `Tey.Version.number` → download+verify+extract → swap ebin
     via `Tey.Toolchain.publish` → swap `bin/tey`/`bin/kex` via
     `FS.File.rename`.
   Reuses `Tey.Toolchain.{repository, releaseBase, releaseTag, download,
   verifyArchive, publish}` and `Tey.Cache.root`; adds no new C++ natives,
   no new stdlib module — same `Process.run("curl"/"tar", ...)` shell-out
   idiom as the rest of `tey/`.

3. **`tey/src/tey/cli.kex`**:
   - Register the command in the `parser` builder (near `kex install`,
     around line 113):
     ```
     .command("upgrade", "", "download and install the newest Tey release") do |_|
       Tey.Cli.upgradeSelf()
     end
     ```
   - Add a `foul upgradeSelf -> Integer` handler in the `private do...end`
     block (near `installKex`/`alreadyCurrent`, ~line 187), following the
     exact same success/error printing style (`${Console.GREEN}Installed${Console.RESET}`,
     `${Console.RED}error:${Console.RESET}`) those two already use, and
     reporting the "already the newest version" and "installed by Homebrew"
     cases with their own plain messages.
   - Add `using Tey.SelfUpdate, only: [...]` to the `using` block at the top
     of the file (alongside the existing `using Tey.Toolchain, only: [...]`).

4. **Docs**: remove the "Tey cannot yet manage Tey... there is no
   `tey self update`" bullet from `docs/tey-limitations.md` (the "Tey and the
   packaging that installs it" section, ~line 149), replacing it with a short
   note that `tey upgrade` exists and what it does *not* do (Homebrew installs
   still go through `brew upgrade tey`). Add `tey upgrade` to the command
   surface table in `docs/plan_tey_pm.md` (~line 344, beside `tey update`).

## Verification

- `tey/spec/` already has one `.spec.kex` per module (`toolchain` presumably
  among them) — add `tey/spec/selfupdate.spec.kex` covering the pure/parsable
  parts: extracting a version out of a fabricated `package.kex` manifest
  string, `homebrewManaged?` on a few sample paths, and `currentPrefix`
  parsing of `TEY_EBIN`-shaped strings. Network- and filesystem-touching
  parts (actual download/swap) are out of reach for a unit spec the same way
  `Tey.Toolchain`'s own archive-install path is untested there today —
  matches existing coverage, not a regression.
- Build Tey and run it end-to-end by hand: `cd tey && make build`, then run
  the compiled `tey upgrade` against a real or `TEY_KEX_REPO`-pointed-at-fork
  repository with at least one tagged release carrying a `tey-*.tar.gz`, in a
  scratch `TEY_HOME`/`PREFIX`, and confirm:
  - a prefix one minor version behind downloads, verifies, and swaps, and the
    freshly-swapped `bin/tey --version` reports the new number;
  - re-running immediately reports "already the newest version" and touches
    nothing;
  - with `TEY_EBIN` unset, it refuses cleanly;
  - with a prefix path containing `/Cellar/`, it refuses and names
    `brew upgrade tey`.
- `cd tey && make check` (type-checks without running) to catch the promoted
  `Tey.Toolchain` signatures and the new module's types before the runtime
  smoke test above.
