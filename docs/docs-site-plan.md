# Docs Site Plan: docs.kex.run (guide + book + reference)

> **Status: planned, not started.** The decisions below are settled; the
> sequencing at the end is the implementation order. Work happens mostly in
> this repo; the site repo (`kexhq/site`, kex.run) gets a small cleanup pass
> at the end.

## Motivation

kex.run's `/docs` section is hand-written Astro pages living in the site
repo, while the real reference documentation is generated by docgen
(`tey docs build`) and published to kexhq/docs' `gh-pages` branch. The plan:

- Move all reference-adjacent and long-form content off kex.run onto
  **docs.kex.run**, linking there instead. kex.run keeps the marketing
  surface plus `/install`, `/repl` and `/playground` (the REPL lessons stay —
  they are tied to the interactive panel).
- Keep the autogenerated reference exactly as it is — it is still needed.
- Add hand-written Markdown content: a **language guide** (ported from the
  site's `/docs` pages) now, and a **book/tutorial** (longer, chaptered,
  easier to digest) later through the same pipeline. The URL shape and
  `tey docs prose` both carry a locale segment from the start, so
  **translations** are additive later rather than a redesign.
- docgen stays a **generic documentation-unit tool** — package-backed is its
  convenience default, not its model (the stdlib already proves the
  no-manifest path). Everything site-specific lives in a separate assembler
  package, not in docgen.

## Current state (facts this plan builds on)

- docgen is a built-in Tey command; source in `tey/src/tey/docgen/`
  (~4.4k lines). It parses `.kex` sources into a typed `PackageModel` and
  renders HTML + Markdown + JSON from it. `markdown.kex` is an **emitter**
  (model → md for LLMs); `rdoc.kex` handles doc comments only. There is no
  Markdown **parser** anywhere.
- `tools/build-docs.sh` builds every release tag from git worktrees plus the
  unreleased checkout (`SKIP_TAGS=1` skips the tag loop), through the
  **current** toolchain; it copies `tools/docs-assets/icon.png` into the
  output. `.github/workflows/docs.yml` publishes the result to kexhq/docs'
  `gh-pages` via `peaceiris/actions-gh-pages`.
- `--base-url` already defaults to `https://docs.kex.run`
  (`tey/src/tey/docgen/cli.kex`); the workflow currently overrides it with
  `https://kexhq.github.io/docs`. gh-pages has no CNAME file; the custom
  domain is not configured yet.
- `versions.json` accumulates across builds (read disk, upsert, union —
  `index.kex` `accumulateVersions`). **`llms.txt`, `llms-full.txt` and
  `sitemap.xml` do not**: each build overwrites them with only its own
  pages, so the last build wins. The assembler fixes this.
- `tey run` executes a package entrypoint on the BEAM (`tey/src/tey/cli.kex`);
  manifests support named entrypoints.
- **The stdlib is not a Tey package and never has been.** `src/stdlib` has no
  `package.kex`; `Tey.Docgen.Index.defaultPackage`/`defaultVersion` fall back
  to `"prelude"` / `Kex.Kernel.VERSION.release` specifically for this case,
  and `index.kex`'s own comment calls it **"the original use"** of docgen.
  `PackageModel` carries `preludeModules`/`preludeSource`/`preludeDoc` only to
  render it. So docgen's real abstraction is *a named, versioned
  documentation unit*, discovered from a `package.kex` when one is standing
  in the CWD and given explicitly (`--source`/`--package`/`--release`) when
  it isn't — package-backed is the convenience default, not the model.
  `tey docs prose` for `docs-src/guide` already follows the no-manifest path
  (invoked with explicit flags from `build-docs.sh`, not `cd package && …`),
  same as prelude — it is the second consumer of an existing pattern, not a
  new one.
- Site repo: 9 hand-written pages under `src/pages/docs/` (overview, syntax,
  types, functions, pattern-matching, purity, traits, operators, prelude)
  using `DocsLayout` + `Code` components; nav data in `src/data/docs.ts`.
  The operators page has a table; overview has a blockquote — the Markdown
  subset must cover both.

## Target site layout

```
/                            landing: Guide / Book / Tutorial / Reference cards, language switcher
/guide/<version>/<lang>/…    hand-written guide, built per release, per locale
/book/<version>/<lang>/…     the book (later), same pipeline, chaptered
/tutorial/<version>/<lang>/… a tutorial (later) — authored AS a book (see below), same pipeline
/prelude/<version>/…         autogenerated stdlib reference (unchanged, English-only, source-derived)
/tey/<version>/…              autogenerated tey reference (unchanged, English-only)
```

Guide and book are **versioned like reference**: built from each tag
worktree's `docs-src/`, so an old version's docs stay historically accurate.
Old tags predate `docs-src/` and are skipped by the existing
dir-exists convention. `/guide/` (no version, no locale) is an alias
redirect to the latest version in the default locale, same pattern as the
existing site-root redirect. `/guide/<version>/` (no locale) redirects to
`/guide/<version>/en/`.

**Locale is a prose-only axis.** Reference (`/prelude/`, `/tey/`) is
generated from source and doc comments, which are English — it stays
unversioned-by-locale, and every guide locale links into the same
reference. Only hand-written prose (`docs-src/guide`, `docs-src/book`) gets
a `<lang>` segment. Content lives at `docs-src/guide/<lang>/*.md` (default
locale `en` required; others optional and allowed to lag); `tey docs prose`
gains a `--locale <lang>` option, defaulting to `en`, that only affects the
output path and an `<html lang>`/hreflang tag — it does not otherwise
change rendering. **Open question, not resolved by this plan:** whether
non-`en` content is human-translated or machine-translated, and whether a
locale build missing a page falls back to English or omits it (recommend:
fall back to English per-page rather than blocking a build, so a partial
translation is never worse than no translation).

**Book/tutorial is a chaptering mode of the same prose pipeline, not a
separate one.** The guide is a flat, `order`-derived list of pages with
prev/next. A book needs nested structure (parts → chapters) and a
generated table of contents; that's `Tey.Docgen.Md` frontmatter growing a
`part`/`chapter` key (or a `SUMMARY.md`-style manifest read by `tey docs
prose`) and the renderer growing a TOC sidebar — additive to the guide's
flat-page rendering, not a fork of it. A "tutorial" is authored as a book
with a linear chapter list; there is no separate tutorial pipeline unless a
later requirement needs *interactive/executable* content (runnable
snippets wired to the playground) — that would be a genuinely new feature,
not a naming variant, so flag the distinction if it comes up.

## Architecture: three layers

The constraint that shaped this: docgen's real job is documenting a *named,
versioned unit* — package-backed is the common case, but its biggest
existing consumer (the stdlib) has no `package.kex` and is documented
through the same explicit-flags path `tey docs prose` uses (see "Current
state"). Either way, docgen must not absorb kexhq site concepts (landing
pages, books, guide↔reference cross-links, locale switcher, CNAME). The
chrome (layout, CSS, highlighting, escaping) lives inside tey-internal
docgen modules, so a separate tool cannot import it — which decides where
rendering lives.

### Layer 1 — docgen gains generic capability only

1. **`Tey.Docgen.Md`** (new `tey/src/tey/docgen/md.kex`, plus spec tests in
   `spec/`): a Markdown parser — pure `String` → typed AST → HTML. Covers
   what the ported pages use: frontmatter (`title`, `description`, `order`,
   later `part`/`chapter` for book/tutorial nesting), headings h1–h4,
   paragraphs, fenced code blocks (```kex runs through `highlight.kex`),
   inline code/bold/italics/links, nested lists, GFM tables, blockquotes.
   No site vocabulary.
2. **`tey docs prose`** subcommand: options
   `--source <md-dir> --out <dir> --package <name> --release <v> --label <text> --base-url <url> --locale <lang>`
   (`--locale` defaults to `en`; affects only output path and `<html
   lang>`/hreflang, not rendering). Renders an md tree into the shared
   chrome at the given out dir, upserts `versions.json` the same way
   `build` does — keyed by (package, version, locale) once locale exists —
   writes a per-prose manifest. Semantics: "long-form docs for a thing with
   a version, optionally a locale". Any package may use it for its own
   docs; nothing in it knows about guides, books, tutorials or the kexhq
   site.

`tey docs serve` already serves the output tree, so local development of
prose works unchanged.

### Layer 2 — the site assembler is a Tey package

**`tools/docsite/`** — its own package (`package.kex` + entrypoint, run via
`tey run` from `build-docs.sh`). This is where all specialization lives:

- the landing page (cards for Guide / Book / Tutorial / Reference, latest
  versions read from the on-disk `versions.json`, plus a language switcher
  once a locale has more than `en`);
- the `/guide/` → latest-version alias redirect, and `/guide/<version>/` →
  `/guide/<version>/en/`;
- **aggregation** of `llms.txt`, `llms-full.txt` and `sitemap.xml` across all
  manifests on disk (fixes the last-build-wins overwrite; sitemap gets
  hreflang links across a page's locale siblings once locale exists);
- writing `CNAME` (`docs.kex.run`) alongside the existing icon copy.

It composes with docgen via files (`versions.json`, manifests), not imports.

### Layer 3 — orchestration

- **Content**: `docs-src/guide/en/*.md` in this repo — the 8 site pages
  ported (overview, syntax, types, functions, pattern-matching, purity,
  traits, operators; the prelude page becomes a guide entry linking into
  the reference index). `Code.astro` blocks become fenced kex. Frontmatter
  carries `title`/`description`/`order`; prev/next and the sidebar derive
  from `order`. Other locales are additional `docs-src/guide/<lang>/*.md`
  directories, added when translations exist — none ship at launch.
- **`tools/build-docs.sh`**: in the tag loop *and* the unreleased pass, after
  each `docs build`, run `tey docs prose` once per locale directory found
  under `docs-src/guide/` —
  `tey docs prose --source <tree>/docs-src/guide/<lang> --out <out>/guide/<version> --package guide --release <version> --locale <lang>`
  (skipped when `docs-src/guide/` is absent entirely); the final step runs
  the docsite package.
- **Workflow**: set `BASE_URL: https://docs.kex.run` (the cli default — just
  stop overriding it) and let `tools/docs-assets/CNAME` reach the output.

## Domain setup (manual, external to the repos)

1. DNS `CNAME docs.kex.run → kexhq.github.io`.
2. kexhq/docs → Settings → Pages → Custom domain `docs.kex.run`, enforce
   HTTPS. The CNAME file arrives via the build; GitHub needs the DNS record
   to verify.

## Site repo cleanup (after docs.kex.run publishes)

- Astro redirects in `astro.config.mjs` mapping the nine `/docs/*` paths to
  their `docs.kex.run/guide/…` counterparts. GitHub Pages is static hosting,
  so these are meta-refresh + canonical HTML redirects, not literal 301s.
- Delete `src/pages/docs/*`, `src/layouts/DocsLayout.astro`,
  `src/data/docs.ts`; point Nav/Footer "Docs" at `https://docs.kex.run`.
- Keep `/install`, `/repl`, `/playground`, and the REPL tutorial data.

## Decisions and rejected alternatives

| Decision | Rejected alternative | Why |
|---|---|---|
| Markdown rendering inside docgen as a generic `prose` subcommand | Doing #171 (Template engine) first | The md parser is needed regardless; #171's M5 retemplating can absorb the prose renderer later without redesign. Not a prerequisite. |
| Same | External SSG (mdBook/Jekyll) for prose | Second toolchain and visual identity; cross-links to reference by URL convention only. Also loses the shared chrome, which is tey-internal. |
| Same | docgen untouched, md rendering in the assembler | The assembler cannot `using` tey-internal modules; it would have to duplicate layout/CSS/highlight. |
| Specialization in a separate `tools/docsite` package | Site spine inside docgen | docgen stays a generic documentation-unit tool (package-backed is its convenience default, not a requirement — see prelude); the assembler is a small, promotable unit (its own package, publishable, or replaceable by an external SSG later without touching docgen). |
| Per-release guide/book | Unversioned prose (built once from current checkout) | Old versions' docs stay historically accurate, consistent with reference. Cost: prose renders per tag worktree — acceptable; old tags simply skip. |
| Guide now, book later | Both at once | The pipeline is identical for both; the book needs writing time and shouldn't block the move. |
| Book/tutorial as one chaptering mode of the prose pipeline | A separate tutorial pipeline/renderer | Same md → chrome pipeline, just nested TOC instead of flat order; a second renderer would duplicate the parser, chrome and versioning for no gain unless tutorials need to be interactive (a different feature, not covered here). |
| Locale as a path segment on prose only (`/guide/<version>/<lang>/…`), reference left unversioned-by-locale | Locale on the whole site, including reference | Reference is generated from English source/doc comments; translating it would mean translating docstrings in `.kex` sources themselves, a different and much larger project. Prose is where translation effort actually goes. |
| `--locale` defaults to `en`, falls back to English per missing page | Require every locale to be complete before publishing | A partial translation is strictly better than none; blocking on completeness would stall every locale indefinitely. |

## Sequencing

1. **A** — `Tey.Docgen.Md` + `tey docs prose --locale` (Layer 1), with
   specs. The locale flag and per-locale output path ship now even though
   only `en` content exists at launch — retrofitting a path segment after
   URLs are live is the expensive version of this, doing it up front is not.
2. **B** — port content to `docs-src/guide/en/`; `tools/docsite/` package
   (landing page with the language switcher, even if it only lists `en` for
   now); `build-docs.sh` + workflow changes (Layers 2–3). Verify locally
   with `tey docs serve` and a full `build-docs.sh` run into a scratch dir.
3. **C** — domain setup (can start in parallel; DNS propagation).
4. Publish, then **D** — site repo cleanup and redirects.

## Follow-ups (out of scope here)

- The book (`docs-src/book/en/`, chaptered via Layer 1's `part`/`chapter`
  frontmatter): one more prose invocation, one more landing card, same
  pipeline.
- A tutorial, if content ends up wanting it as a distinct thing from the
  book rather than just a differently-organized set of chapters.
- Non-`en` guide/book content: translation workflow (human vs. machine),
  and whether it's tracked per-page for staleness against the `en` source —
  the URL shape and `--locale` flag are ready for this; the content and
  process are not designed here.
- #171 M5 porting docgen (and the prose renderer) onto `.ket` templates —
  the prose work is one more consumer, not an obstacle.
- Guide↔reference deep links beyond the prelude page entry point, if the
  link-index mechanism grows a prose-aware mode (must stay generic).
